# UniGraph 旧版与当前版详细对比审计报告

> 审计对象：`docker_unigraphonline.zip` 与当前 `D:\PycharmProjects\UniGraph` 工作区
>
> 审计日期：2026-08-04
>
> 旧版压缩包时间：2026-06-27 21:02:59
>
> 旧版压缩包 SHA-256：`42B1FF30AAC17FD047561F6D8DF7F6C9E3A811A2EBB66BF8922B7FC802A3ED90`
>
> 当前 Git 基线：`40a161de2a7f0e4ebc93ac270bda6aa41d311e23`，并包含审计时尚未提交的本地修改

## 1. 结论先行

当前版不是“所有方面都优于旧版”，但也绝对不适合整体回退到旧版。

综合判断如下：

- 当前版在开源安全、多用户隔离、任务权限、聊天持久化、分享、问答恢复、引用展示、模型配置、部署文档和自动化测试方面明显优于旧版。
- 旧版在默认索引速度、前端状态组织、国际化完整度和部分成熟组件交互方面优于当前版。
- 当前版最明确的性能退化是：旧版索引深度由用户选择且默认 `1`，当前版前端不再传递深度，后端固定使用 `4`。这会递归生成更多层社区，并为更多社区调用大模型生成报告。
- 当前版最大的工程风险是前端采用“Vue 页面壳 + 大型原生 JavaScript 控制器 + 直接 DOM 操作”的混合架构。它降低了依赖数量并实现了新设计，但用户信息、历史对话、问答任务和弹层状态更容易出现重复状态与生命周期竞态。
- 当前版把问答放进 Celery 后实现了切换页面、刷新恢复和后台执行，但问答、索引、知识迁移仍共用同一任务队列，Celery 停止或长任务占满 worker 时，交互式问答也会受到影响。
- 当前版后端核心知识图谱算法并没有被全面重写。大量工作集中在产品层、安全层、任务编排和展示层。因此“优化版”不等于“知识抽取和索引算法一定更快”。

建议：以当前版为主线继续，不做整体回滚；开源前优先修复索引深度、任务队列隔离、HTTP 连接复用、批量向量、前端端到端测试和剩余的结构化输出边界检查。

## 2. 审计范围与方法

本次对比使用以下方法：

1. 解压旧版压缩包并计算 SHA-256，保证对比对象明确。
2. 排除 `.git`、`node_modules`、`dist`、缓存、运行日志和临时数据后，比较文件清单和内容哈希。
3. 对共同业务文件逐模块检查后端、前端、Celery、索引、问答、模型配置、安全、部署和测试。
4. 对当前版执行后端测试、Ruff、运行时导入、前端 ESLint、类型检查和生产构建。
5. 尝试在独立临时目录安装旧版前端依赖；由于系统盘空间不足，安装未完成，因此没有把旧版标记为“构建失败”。

限制：

- 旧版压缩包没有 Git 历史，无法精确区分每一项变化来自哪一次提交或哪位优化者。
- 当前工作区不是干净发布快照。审计开始时有 48 项已修改或未跟踪内容，因此报告描述的是“当前真实工作区”，而不只是当前 Git 提交。
- 当前项目没有浏览器端到端自动化测试。悬浮引用、拖动、下拉滚动、头像同步和聊天切换等交互只能通过代码审计与人工使用记录评估。
- 旧版前端依赖安装因系统盘空间不足中止，不能用当前机器给出旧版构建是否成功的最终结论。

## 4. 总体架构差异

### 4.1 旧版架构

旧版前端主要是传统 Vue 3 单文件组件结构：

- Vue Router 统一路由。
- Pinia/Vuex store 管理知识库、图谱、实体、关系和聊天状态。
- Vuetify、Arco Design、Element Plus 等组件库承担弹窗、表单、下拉和滚动交互。
- `vue-i18n` 使用中英文 locale 文件管理翻译。
- 图设计与构建页面主要集中在大型 Vue SFC 中。
- 问答走 FastAPI NDJSON 流式接口，浏览器连接断开后任务过程随之丢失。

旧版后端已经是 FastAPI + Celery + MySQL + Redis，并已包含实体关系抽取、社区划分、社区报告、向量索引和结构化检索。

### 4.2 当前版架构

当前版前端是混合架构：

- Vue 组件负责页面壳和局部响应式状态。
- 业务交互大量迁移到 `frontend/src/controllers/*.js`。
- 控制器直接查询 DOM、拼接 HTML、绑定全局事件并维护模块级变量。
- 通用 API 从 Axios 模块拆分改为统一的原生 `fetch` 客户端。
- 移除 Pinia/Vuex、Vuetify、Arco、Element Plus 和 `vue-i18n`。
- 路由全部使用动态导入，图运行时只在设计/构建页面加载。
- 问答默认通过 Celery 提交，前端轮询任务状态并逐步展示检索过程和部分答案。

当前版后端在原有核心算法外增加了：

- 多用户资源所有权检查。
- 任务所有权、任务白名单和接口限流。
- 模型密钥加密和外部模型地址校验。
- 规范化聊天消息、信息源和分享快照表。
- 滚动历史对话上下文和摘要。
- 结构化任务进度、错误状态和 Redis 失败详情缓存。
- 开源文档、CI、Dependabot、Compose 和 systemd 部署文件。

## 5. 后端能力详细对比

### 5.1 知识图谱核心算法

结论：核心流程被保留，当前版不是全新的算法实现。

共同流程仍然是：

1. 文档读取与分段。
2. 实体类型匹配与实体抽取。
3. 关系抽取、类型匹配和溯源。
4. Leiden 社区划分。
5. 每个社区调用聊天模型生成社区报告。
6. 每个实体调用嵌入模型生成属性向量。
7. 将社区、向量和映射逐条写入数据库。

当前版在少数解析环节增加了边界处理，例如关系类型匹配时捕获 `IndexError`，社区报告 JSON 围栏清理和评分范围限制。但抽取责任链里仍存在 `ins1_output[0]`、`ins2_output[0][0]` 等直接索引。模型返回空结构或异常结构时，仍可能出现 `list index out of range`。

判断：当前版的抽取稳定性有所提高，但没有彻底消除结构化模型输出不可信的问题。

### 5.2 索引构建

这是当前版相对旧版最需要警惕的部分。

旧版：

- 建立索引前显示“索引深度”弹窗。
- 默认深度为 `1`。
- 用户选择的 `depth` 被传给 Celery，再传给 `CommunityDetection(max_level=depth)`。
- 社区报告并发为 `50`。
- 实体向量并发为 `100`。

当前版：

- 前端提交建立索引任务时只提交图谱 UUID 和 token，没有提交索引深度。
- Celery 任务签名虽然保留 `depth=4`，真正调用服务时直接写死 `level=4`。
- 索引完成后数据库深度也直接写成 `4`。
- 社区报告并发仍为 `50`，实体向量并发仍为 `100`。

影响：

- 并发数没有提升，工作量却从默认递归 1 层变成固定递归 4 层。
- 社区检测会保存递归层级中的社区，并为社区生成报告，因此模型请求数通常增加。
- 当前任务中出现 62 份社区报告，与固定深层社区划分一致。
- 单纯增加 Celery worker 并不能缩短一个索引任务内部的所有网络请求和串行数据库写入。

另外还有三项性能差异：

1. 旧版实体向量代码写死了一个第三方嵌入服务及明文密钥；当前版使用用户配置的嵌入模型。旧服务如果更快，会让旧版显得更快，但该实现不能恢复。
2. 两版都为每个社区单独请求一次聊天模型、为每个实体单独请求一次嵌入模型，没有批量嵌入。
3. 当前版每次请求都创建并关闭一个新的 `AsyncOpenAI` 客户端，缺少跨请求连接池复用；旧版也每次新建客户端，但没有关闭，表面上可能少一点关闭开销，却存在资源泄漏。

结论：旧版索引更快的首要原因是默认工作量更小，其次可能是旧版写死的嵌入服务更快。不是旧版 Celery 并发更高。

### 5.3 向量失败处理

旧版对单个实体向量失败的处理是记录错误并继续返回实体，可能最终得到部分实体没有有效向量的“不完整成功索引”。

当前版会收集失败项，只要存在失败就抛出错误，让任务进入失败状态。

这是正确性提升，但会让当前版比旧版更容易显式失败。不能为了“快”恢复旧版吞错逻辑。

### 5.4 Celery 任务系统

当前版的改进：

- 新增知识问答 Celery 任务。
- 任务状态包含进度、详情、检索结果和最近 60 条日志。
- 失败时将结构化错误缓存到 Redis，并真正抛出异常让 Celery 状态为 `FAILURE`。
- 查询、撤销任务前检查任务所有者。
- 任务提交使用白名单，不能任意执行已注册任务。
- 提交长任务前检查知识库、架构和图谱归属。
- 任务提交接口增加限流。

旧版的问题：

- 任务状态和结果接口只凭任务 UID 查询，没有用户所有权检查。
- 提交接口没有任务白名单。
- 构建索引等任务捕获异常后直接 `return error_payload`，Celery 可能把错误当作普通成功返回。

当前版的新风险：

- 问答、索引、架构构建和知识迁移没有配置独立队列。
- 所有任务共享同一 Redis broker 和 worker 池。
- 当前默认 worker 并发为 `4`；长索引和迁移任务可以占用交互式问答的执行槽位。
- 前端问答默认依赖 Celery。Celery 停止时，旧版直接 API 问答原本可以工作，当前 UI 则会卡在任务等待。
- 后端仍保留直接 NDJSON 问答接口，形成“直接流式 + Celery”双路径，但前端主路径只使用 Celery，维护成本增加。

结论：当前版任务安全和可观察性明显更好，但应该拆分 `interactive_qa`、`indexing`、`migration` 队列，而不是继续只加同一队列的并发数。

### 5.5 问答与上下文

旧版：

- 浏览器调用 `/ask/{uuid}` 并保持 NDJSON 连接。
- 主要只等待最终结果和心跳。
- 页面刷新或离开后，浏览器侧无法持续展示过程。
- 聊天库主要用一个 JSON 字段保存消息，没有规范化的消息和信息源表。

当前版：

- 问答作为后台任务运行。
- 每 500ms 获取任务状态。
- 可展示模型配置、实体、关系、信息源、社区报告和历史对话上下文。
- 模型生成过程中保存部分答案，刷新或切换回来可以恢复。
- 用户消息、助手消息、模型、effort 和四类信息源分别持久化。
- 支持滚动历史上下文、旧对话摘要、token 预算和当前问题截断边界。
- 支持只读分享快照、更新、轮换和撤销链接。
- Prompt 要求与提问语言一致，并在图谱和历史都不足时使用通用知识，同时明确声明不是来自当前图谱。

这是当前版实质性提升。但问答后台恢复功能曾引入同一任务被前台和全局恢复监听器重复渲染的问题，说明双通路状态协调仍是高风险区。

### 5.6 模型配置

两版都已有“提供商 + 多个模型”的后端基础结构，不应把多模型能力完全归功于当前版。

当前版新增或完善：

- API Key 加密存储。
- 浏览器接口只返回掩码，不回传真实密钥。
- 模型提供商名称从全局唯一改为用户内唯一。
- 模型提供商自定义顺序，默认使用第一项。
- 语言模型与嵌入模型按类型选择。
- 调用模型前验证外部 URL，默认阻止私网和本地地址，降低 SSRF 风险。
- 兼容旧用户字段，并在实际使用时迁移旧明文密钥。

代价：

- 配置链路更复杂，错误配置会影响索引与问答。
- 当前索引速度取决于用户选择的嵌入服务，不再偷偷使用旧版写死的服务。
- 模型拖动排序、默认模型和缓存同步新增了较多前端状态逻辑。

### 5.7 数据库与多用户隔离

当前版的关键改进：

- 知识库名称从全局唯一改为用户内唯一。
- 模型提供商名称从全局唯一改为用户内唯一。
- 图谱、架构、实体、关系、聊天和任务操作增加所有者校验。
- 聊天拆分为 `chat_library`、`chat_message`、`chat_message_source`、`chat_share`。
- 新增模型排序字段。

风险：

- 升级迁移依赖按顺序手工执行 `backend/migrations/*.sql`。
- 目前没有看到统一迁移版本表自动记录这些手工 SQL 是否已执行。
- 部署者遗漏迁移会导致聊天、分享、多用户约束或模型排序出现运行时错误。

建议后续将这些迁移纳入 Alembic，至少增加启动前的 schema 版本检查。

## 6. 前端详细对比

### 6.1 依赖和加载性能

当前版的明确提升：

- 运行依赖从 33 个下降到 13 个。
- 移除三个 UI 组件体系、Pinia/Vuex、Axios、`vue-i18n` 和多个未使用图布局插件。
- 路由页面全部动态导入。
- Cytoscape 图运行时只在图设计和构建页面加载。
- 当前生产构建中最大业务图块被拆分，普通页面不需要一次加载全部图可视化代码。

新的部署风险：

- 动态导入依赖带哈希的 chunk 文件。
- 如果部署时 `index.html` 与 `assets` 不是原子替换，或浏览器/代理缓存了旧 HTML，就会出现 `Failed to fetch dynamically imported module`。
- 旧版核心页面多为静态导入，发生这种错误的概率较低。

因此当前版部署必须确保：先完整上传新 assets，再切换 HTML；HTML 不做长缓存；旧 assets 延迟清理。

### 6.2 状态管理与可维护性

旧版虽然文件多、组件库重，但状态边界更符合 Vue：store、组件 props、响应式变量和 locale 文件比较明确。

当前版主要控制器规模：

| 文件 | 行数 |
|---|---:|
| `GraphApplicationView.js` | 1,944 |
| `GraphBuildView.js` | 1,352 |
| `GraphDesignView.js` | 1,106 |
| `ProfileView.js` | 688 |
| `task-manager.js` | 556 |
| `i18n.js` | 848 |
| `AppSidebar.vue` | 572 |

这些控制器同时承担 API、状态、DOM、动画、弹层、滚动和生命周期，导致以下类型的回归反复出现：

- 个人中心头像、侧边栏头像和本地缓存不同步。
- 修改用户名后缓存与后端身份不一致。
- 从不同页面新建对话时历史记录和索引列表丢失。
- 当前问答与后台恢复监听器重复渲染同一思考面板。
- 引用弹层在 hover、popover 顶层和页面边界之间互相影响。
- 下拉列表、模态框和页面滚动容器抢夺滚动事件。
- 任务日志自动滚动覆盖用户手动上滑。

结论：当前 UI 视觉方向可以保留，但不应继续把所有新功能堆进这些控制器。至少要把用户、聊天、任务和弹层状态拆成可测试的 composable/store。

### 6.3 国际化

旧版：

- 使用 `vue-i18n`。
- 页面和图组件有独立中英文 locale 文件。
- 组件通过 key 获取翻译。

当前版：

- 使用自定义 `t()`、静态映射和正则替换。
- 还需要翻译后端动态日志、任务详情和运行时拼接文本。
- 字符串分散在 Vue、控制器和后端中。

当前方案短期改动快，但完整性和可维护性不如旧版。这与用户多次发现“还有很多地方没有英文化”一致。

建议恢复 key-based 国际化机制，不一定恢复全部旧 UI，但应恢复 `vue-i18n` 或等价的结构化字典管理。

### 6.4 图可视化

旧版：

- 小图使用 `cose-bilkent`。
- 中图使用 `fcose`。
- 大图使用 `dagre`，偏层次布局。
- 引入 Klay，但没有发现明确的实际布局调用。

当前版：

- 普通模式继续使用 `cose-bilkent` 和 `fcose`。
- 大图通过 draft `fcose`、标签降级、纹理视口等方式控制性能。
- 负载模式引入 vis-network、聚类、双击展开、停止物理模拟和视口恢复。
- 增加数据库、简约、多彩、负载等产品展示模式。

当前版对大型图谱做了更多性能防护，但前三种全量模式仍可能因为大量标签互相遮挡而可读性不足。旧版 `dagre` 的层次布局在某些有方向图上可能更清晰。

建议把 `dagre` 作为可选布局恢复，而不是替换当前负载模式。

### 6.5 聊天与引用

当前版新增：

- 四类来源映射：整体知识概览、具体信息来源、相关知识关联、重点知识细节。
- 从回答中的 `[Data: ...]` 解析记录 ID，并映射回结构化来源。
- 引用就近展示、同类型连续合并、悬浮/点击弹层、顶层 popover 和高度限制。
- 分享页复用相同的 Markdown 与引用渲染工具。
- 思考过程展示实体、关系、原文和社区报告。
- 复制、重新生成、编辑和删除消息。

旧版有基础索引引用格式，但没有当前版完整的结构化消息来源持久化与分享一致性。

当前版功能更强，不过交互实现跨 `GraphApplicationView.js`、`SharedChatView.vue`、`chat-content.js` 和 CSS，仍需要浏览器自动化防止再次出现弹层消失、越界和层级覆盖。

### 6.6 旧版存在、当前版弱化或移除的入口

1. 旧版索引深度弹窗已移除，当前后端固定为 4。这是明确退化。
2. 旧版导出索引弹窗同时支持下载文件和生成 URL；当前构建页只直接下载文件，后端 URL 接口仍在，但 UI 入口没有保留。
3. 旧版存在 `/auth/callback` 页面和 SSO 登录流程；当前前端没有该路由。旧版 SSO 后端存在安全绕过风险，因此不能直接恢复，若确实需要应重新安全实现。
4. 旧版有专门 404 页面；当前未知路由直接重定向到工作区。功能损失较小，但排错信息减少。
5. 旧版使用结构化 `vue-i18n`；当前改成自定义翻译器，国际化完整度下降。

## 7. 安全与开源准备度

### 7.1 旧版不适合直接开源

旧版扫描发现 7 个包含高置信度密钥或私钥模式的文件，具体值未在报告中展示。旧版压缩包还包含：

- 后端真实环境文件。
- 开发和生产环境文件。
- 前端私钥、证书、PFX 和密码文本。
- 多处硬编码模型 API Key。
- 前端硬编码认证 AES Key。
- 本地向量索引数据。
- 数据库 SQL 快照。

旧版任务接口缺少任务所有权和任务白名单，部分模型测试接口和上传接口也缺少当前版的防护。

最严重的是旧版内置许可证过期时间为 `2025-09-30`，后端启动时校验失败会直接 `sys.exit(1)`。在当前日期，旧版原样启动会被自身许可证拦截。

### 7.2 当前版的安全提升

当前版已经加入：

- AGPL-3.0 许可证、第三方声明、安全政策和贡献指南。
- 模型 API Key 加密和接口掩码。
- 高置信度密钥扫描回归测试。
- 上传认证、扩展名、文件名、大小和图片内容验证。
- 不再公开挂载原始上传目录。
- LLM 外部 URL 校验。
- 登录、注册、验证码、模型测试和任务提交限流。
- 多用户资源所有权检查。
- 任务所有权和任务执行白名单。
- 生产环境关闭 OpenAPI 文档。
- 通用异常不向前端返回完整堆栈和本地变量。
- 注册唯一键冲突转换为简短业务错误。

当前 `git ls-files` 检查显示，运行时上传文件没有被 Git 跟踪，只有 `.gitkeep` 和默认知识库图片被跟踪。

### 7.3 当前仍需注意

- 分享链接公开接口没有认证，依赖不可猜测的 UUID；建议增加访问频率限制。
- 手工 SQL 迁移应纳入版本管理工具。
- 构建索引失败详情目前仍可能直接包含底层模型错误文本，公开部署时应进一步分离用户消息和内部日志。
- 在真正开源前必须重新扫描 Git 历史，而不只是当前工作树。

## 8. 文档、部署和运维

当前版明显更完整：

- README 有产品故事线、架构、功能、部署、贡献和许可证说明。
- 技术文档中包含设计、构建和检索架构图。
- 有开源检查表、安全政策、贡献指南和第三方声明。

旧版包含多套 Dockerfile、Compose、PM2 和证书文件，但安全边界和开源说明不足，且许可证会阻止当前日期启动。

## 12. 应从旧版恢复或借鉴的内容

### 必须恢复

1. 建立索引时允许选择深度，默认建议 `1` 或 `2`，后端不得再写死 `4`。
2. 恢复结构化、key-based 国际化，不再依赖散落字符串和正则替换。

### 建议恢复

1. 把 `dagre` 作为大图可选布局，而不是替换当前负载模式。
2. 恢复“导出索引 URL”的 UI 入口，后端接口已经存在。
3. 借鉴旧版 store 思路，建立统一用户、聊天和任务状态源。
4. 如果确实需要 SSO，按当前安全标准重做 Auth Callback，而不是恢复旧版绕过实现。

### 不应恢复

1. 写死第三方嵌入地址和 API Key。
2. 失败后吞掉异常并把不完整索引当成功。
3. 任务接口无所有权检查和任意任务执行。
4. 公开打包 `.env`、私钥、PFX、密码和本地向量数据。
5. 硬编码前端认证密钥。
6. 已过期的启动许可证检查。
7. 未实际接入主业务的整套内嵌 Docling 源码。

## 13. 开源前整改优先级

### P0：开源前必须完成

4. 将当前 48 项本地修改整理成可审计提交，再基于干净工作树做最终发布检查。
5. 重新扫描完整 Git 历史中的密钥、证书和环境文件，并轮换旧版已暴露的所有密钥。
6. 对结构化抽取链补齐空列表、错误元组和模型非预期输出验证，彻底消除 `list index out of range`。

### P1：强烈建议完成

1. 为聊天和嵌入请求复用 `AsyncOpenAI` 客户端与 HTTP 连接池。
2. 嵌入接口支持批量输入，减少 107 个实体对应的 107 次独立网络请求。

4. 社区、向量和映射使用批量数据库写入。

7. 将手工 SQL 纳入 Alembic 或增加 schema 版本检查。

### P2：后续优化

1. 恢复 dagre 可选布局。
2. 恢复索引 URL 导出入口。
3. 对大型控制器按业务边界拆分并增加单元测试。

## 14. 最终判断

如果只看“建立索引需要多久”，旧版当前默认行为优于当前版；这是当前版明确退化，必须修正。

如果看完整产品和开源要求，当前版明显优于旧版。旧版包含高风险密钥和证书、缺乏资源所有权、任务接口过宽、错误状态不可靠，并且许可证已经过期，不能作为公开发布基线。

因此最合理的路线不是回退，而是：

1. 保留当前版的安全、聊天、任务、引用、分享、文档和部署能力。
2. 恢复旧版“低深度默认 + 用户可选”的索引策略。
3. 用独立队列、连接池、批量嵌入和批量写入解决真实性能问题。
4. 用统一状态源和浏览器 E2E 测试控制当前前端架构带来的回归风险。

完成这些项目后，当前版才能同时在功能、安全和性能上稳定超过旧版，而不是只在功能和界面上更丰富。
